# GitHub Repo Analyzer

A small FastAPI app that takes a public GitHub repository (URL or `owner/repo`) and shows its metadata, contributors, commit activity, and commit-frequency metrics from the GitHub REST API — plus an optional AI brief generated by OpenRouter. Public repos work with no tokens at all; private repos work with a token you paste into the form for that one request.

## Run it

### Locally with uv

```sh
uv sync
uv run uvicorn app.main:app --reload
```

Then open http://127.0.0.1:8000.

### With Docker

```sh
docker compose up --build
```

The app listens on port 8000. `/healthz` is available for health checks.

## Settings

Copy `.env.example` to `.env` and fill in what you need — every setting is optional and the app works with none of them.

| Variable | What it does |
|---|---|
| `GITHUB_TOKEN` | Server-side GitHub token. Raises the shared GitHub limit from 60 to 5,000 requests/hour — that budget is shared by everyone using this instance who doesn't bring their own token. Only needs read access to public repos. |
| `OPENROUTER_API_KEY` | Enables the "Generate AI brief" button. Without it the brief panel just says it's unavailable. |
| `LLM_MODEL` | The OpenRouter model used for briefs. Must support structured outputs (json_schema) on OpenRouter. |
| `LLM_ZDR_ENABLED` | Set `true` to allow briefs for private repos. It makes the app ask OpenRouter to route private-repo briefs only to zero-data-retention providers; the brief fails if the configured model has none. |
| `CACHE_TTL_SECONDS` | In-memory cache lifetime for analyses (default 3600). |
| `LOG_LEVEL` | Python log level (default INFO). |

There is also a **GitHub token** field in the web form. It is different from `GITHUB_TOKEN`: it is used for that single request only, never stored or logged, opens *your* private repos, and gives *you* your own 5,000 requests/hour instead of sharing the instance budget. It needs Metadata and Contents read access on the repo you're analyzing.

The AI brief only runs when someone clicks the button — it's never generated automatically, and the result is stored so the same analysis is never paid for twice. `LLM_ZDR_ENABLED=true` is required before a private repo's data may go to the LLM.

## API

Interactive docs are at `/docs` (Swagger UI). `/api/analyze` also takes an optional `"token"` field for a per-request GitHub token. `/api/brief` returns 200 with `brief: null` and a `reason` when a brief isn't possible (no LLM key configured, or a private repo without `LLM_ZDR_ENABLED`). Errors are `{"detail": ...}` with status 400, 403, 404, 429, or 502.

Analyze a repo:

```sh
curl -X POST http://localhost:8000/api/analyze \
  -H "Content-Type: application/json" \
  -d '{"repo": "octocat/Hello-World"}'
```

Generate a brief for a stored analysis (the `analysis_id` comes back from `/api/analyze`):

```sh
curl -X POST http://localhost:8000/api/brief \
  -H "Content-Type: application/json" \
  -d '{"analysis_id": "<analysis_id>"}'
```

On Windows PowerShell use `curl.exe` instead of `curl` (the built-in `curl` alias is `Invoke-WebRequest`).

## How it works

The form or `/api/analyze` goes to `main.py`, then `service.py` checks the cache, calls GitHub in parallel and runs the analyzer, and the result is rendered as HTML or returned as JSON. The "Generate AI brief" button goes to `/brief`, then `service.py`, then `llm.py`.

- `app/main.py` — routes and error handlers only.
- `app/service.py` — coordinates the analysis store, repo-name cache, GitHub client, analyzer, and brief generation.
- `app/github_client.py` — the only module that calls the GitHub API.
- `app/analyzer.py` — pure functions that turn raw GitHub payloads into metrics; no I/O.
- `app/llm.py` — the only module that calls the LLM (OpenRouter).
- `app/templates/` + `app/static/` — Jinja2/HTMX UI with vendored htmx and Chart.js.
- `app/cache.py`, `app/models.py`, `app/errors.py`, `app/config.py` — in-memory caches, Pydantic schemas, typed errors, and settings.

## How the AI brief stays grounded

The LLM never computes numbers. It receives only the computed metrics, repo metadata, and the top 10 contributors as login + commit count (no URLs or avatars), plus the first 8,000 characters of the README — which the system prompt marks as untrusted data, not instructions. The reply must be JSON matching a strict schema where every strength, risk, and getting-started point lists the metric fields that support it; points citing unknown fields (or none) are dropped and the drop count is shown. Code does all the math; the LLM only describes it.

## Known limitations

- Everything is in-memory: analyses expire after `CACHE_TTL_SECONDS` and are lost on restart; there's no history.
- Only complete public analyses are cached by repo name and listed as recent; private and partial results always cost a fresh GitHub fetch.
- Commit-activity stats cover the last 52 weeks; while GitHub is still computing them you get a partial report with a Retry button.
- The "busiest time" punch-card stat is in each committer's local time, not UTC.
- "Open issues" includes pull requests, matching GitHub's own count.
- The all-time commit count covers the default branch only.
- Contributor lists are capped (page 1 without a token, 5 pages with one); the UI says when more exist.
- Without a token you're limited to about 10 analyses an hour (GitHub's 60 req/hour ÷ ~6 calls per analysis); the form token or `GITHUB_TOKEN` raises that.
- The brief depends on the configured OpenRouter model supporting structured outputs; private-repo briefs additionally need `LLM_ZDR_ENABLED=true`.
